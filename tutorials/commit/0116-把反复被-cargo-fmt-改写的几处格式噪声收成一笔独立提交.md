# 把反复被 `cargo fmt` 改写的几处格式噪声收成一笔独立提交

这次提交没有改行为，也没有改性能。

它只解决一个协作问题：有几处 Rust 文件每次跑 `cargo fmt` 都会再次出现格式差异，导致后面的功能提交里反复夹带同样的噪声。

## 为什么这次要单独提交

如果不把这种格式噪声单独收掉，后面会不断发生两件事：

1. 每次真正改功能时，工作树都会额外多出几处无关 diff
2. 每次都要重新判断“这是不是新逻辑”，很浪费注意力

所以更好的做法是：

- 明确承认这几处就是 `cargo fmt` 的稳定产物
- 单独成一笔整理提交
- 以后它们再出现时，就不再和功能/性能提交混在一起

## 这次收了哪些位置

这次只收了三处：

- `rust/src/indicators/indicator/dx.rs`
- `rust/src/indicators/indicator/rsi.rs`
- `rust/src/indicators/simple/mod.rs`

它们的共同点是：

- 只是换行和参数排版
- 没有改控制流
- 没有改算法
- 没有改接口语义

## 为什么这种提交是合理的

很多人会觉得“纯格式提交没价值”，但前提是它不会持续干扰后续工作。

当某些位置已经被证明会被格式器反复改写时，单独提交一次反而更有价值，因为它可以：

- 让以后的功能 diff 更干净
- 让 code review 更聚焦
- 让 AI/人协作时少重复处理同样噪声

## 这次没有包含什么

这次没有把任何 benchmark 产物一起提交。

特别是：

- `c/benchmark_contract` 这种未跟踪二进制产物不应该跟着进仓库

格式收口和生成产物处理应该分开，不要混成一笔。

## 顺手记一个知识点

### 1. 格式提交的正确用法

格式提交不是不能做，而是要满足两个条件：

- 范围小
- 不和行为改动混在一起

只要做到这两点，它就能减少噪声，而不是制造噪声。

### 2. 为什么后续还能避免反复发生

这次之后，如果又出现同样的 `cargo fmt` 改写，我们就可以更快判断：

- 这是格式器稳定输出
- 不是新的行为变化

也就是说，这笔提交相当于给后面的协作“清了一次底”。
