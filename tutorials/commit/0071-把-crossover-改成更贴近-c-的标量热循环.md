# 把 crossover 改成更贴近 C 的标量热循环

这次改动的背景，是前面做二进制对照时发现了一个很典型的问题：`crossover` 这类逻辑本身并不复杂，但 Rust 版本编出来的机器码比 C 复杂得多，结果 benchmark 上反而更慢。

所以这次的目标不是“大改架构”，而是验证一个更直接的问题：

- 如果把 `crossover` 的 batch 热循环写得更贴近 C，
- 让编译器少走那条很重的比较向量化路径，
- 性能会不会明显变好？

答案是：会，而且效果很明显。

## 这次做了什么

我在 Rust 里给 `crossover` 抽了一个专门的批处理 helper：

- `run_crossover_batch(left, right, output)`

然后让：

- `run()`
- `run_in_place()`

都复用这个同一条热循环，而不是各自保留一份高层写法。

这条新热循环故意写得更接近 C：

- 相邻元素前后对照
- 顺序前进
- 直接写输出

而不是继续让编译器去推导更复杂的批量比较向量化。

## 为什么这次有效

之前我做二进制对照时看到：

- C 版 `ti_crossover` 是非常薄的循环
- Rust 版 `Crossover::run_in_place()` 前面有公共契约检查
- 更关键的是，热循环本身还被编成了一大段比较复杂的 SIMD 逻辑

这说明 Rust 的问题不只是“接口税”，还包括：

- 对这个逻辑来说，当前代码形态诱导出了过重的机器码

这次把热循环收紧之后，focused benchmark 结果变成：

- `crossover 4096 = 0.311x`
- `crossover 65536 = 0.511x`

也就是说，Rust 现在不只是追平了，而是这两个档位都明显快于 C。

## 新手知识点 1：源码看起来简单，不代表机器码也简单

很多 Rust 新手会有一个直觉：

> 这段源码挺短，编译出来应该也挺简单。

其实不一定。

像 `crossover` 这种逻辑：

- 有相邻元素依赖
- 有两个条件判断
- 还要输出 `0/1`

如果源码写法让编译器走进“更激进”的自动向量化路径，最后生成的机器码可能比你手写的顺序循环还复杂。

所以性能调优不能只看源码长度，还要适当看：

- benchmark
- 二进制
- 汇编

## 新手知识点 2：`unsafe` 不等于“随便乱来”

这次的 helper 里用了 `unsafe` 指针前进。

这里的关键不是“用了 `unsafe` 就更快”，而是：

- 我们已经在公共接口层做过输入/输出长度检查
- 进入热循环后，剩下的是一段非常规律的内存前进
- 这时用 `unsafe` 可以更明确地表达“这里不要再为每一步重复做边界检查”

所以更准确的理解应该是：

- 安全性保证放在边界层
- 热循环里只保留必要的工作

这是一种很常见的性能敏感 Rust 设计方式。

## 这次最重要的经验

不是所有“向量化得更复杂”的机器码都会更快。

对一些很薄、又带相邻依赖的逻辑来说：

- 更贴近 C 的顺序热循环
- 反而更容易得到稳定、可控、而且更快的结果
