# 0003 第二批 Rust 指标迁移与共享校验层

## 背景

在 `0002` 里，这个仓库已经有了最小 Rust 内核、`sma` / `ema` 两个指标、golden test 和 benchmark 基础设施。
但如果只停在这一步，架构还不算真正经受过考验，因为：

- 还没有覆盖多输出指标
- 还没有覆盖典型 oscillator
- 还没有覆盖更复杂的参数组合
- 还没有覆盖多输入指标的批处理和流式路径

所以第二批迁移的重点，不只是“多搬几个指标”，而是用更多类型的指标去验证第一批搭的抽象有没有足够的表达力。

## 主要目标

这次提交主要解决三件事：

1. 把 `bbands`、`rsi`、`macd`、`atr` 接入 Rust 实现
2. 把输入数量、参数数量、输入长度一致性这些校验逻辑收口到共享 helper
3. 让 benchmark 和测试自动覆盖新注册的 Rust 指标，而不是每加一个指标就手工接一遍

这样做的意义是，后面的迁移会更像“照着模式复制”，而不是每个指标都重新发明流程。

## 改动概览

这次新增了四个 Rust 指标实现：

- `bbands`
- `rsi`
- `macd`
- `atr`

其中：

- `bbands` 代表窗口类、多输出指标
- `rsi` 代表典型平滑 oscillator
- `macd` 代表多参数、多输出、内部依赖多条 EMA 的组合型指标
- `atr` 代表多输入指标，并且补了流式路径

除了指标本身，还做了两个结构性调整：

- 把输入个数、选项个数、正整数参数、三输入长度一致性这些逻辑抽到了共享校验层
- 把流式测试从手工点名 `sma` / `ema` 改成了自动遍历已注册且支持 stream 的指标

这意味着新增指标以后，测试和 benchmark 的覆盖会更自然地跟着走。

## 关键知识

### 1. 为什么这四个指标很重要

这四个指标能覆盖之前没有验证到的几个关键维度：

- `bbands`：三个输出，验证 Rust 输出容器设计是否能处理多输出
- `rsi`：平滑上升/下降量，验证状态型批处理逻辑
- `macd`：三个参数、三个输出，还带 12/26 的特殊 EMA 系数规则
- `atr`：三个输入，还要求流式结果和批处理结果保持一致

如果这些都能通过现有 golden test，说明当前 Rust 内核已经不是只适合最简单指标了。

### 2. 为什么要抽共享校验层

随着指标数量增加，如果每个文件都自己写：

- 输入数量检查
- 参数数量检查
- period 解析
- 多输入长度一致性检查

很快就会出现两个问题：

- 同样的规则在不同文件里写得不完全一样
- 某次修一个边界处理时，要到处同步改

把这些校验收口到共享 helper 的目的，是让“输入是否合法”这件事变成一套统一规则，而不是每个指标各自处理。

### 3. 为什么要让测试和 benchmark 自动扩展

如果每次新增一个指标都要手工去改：

- 测试白名单
- benchmark 白名单
- stream 覆盖名单

那这个迁移过程会越来越难维护。

这次把逻辑改成“从 Rust registry 出发自动发现”之后：

- 新指标只要注册，就会自动进入 batch benchmark
- 支持 stream 的指标会自动进入 stream 对比测试
- 覆盖面更不容易漏

这对后面持续自动迭代优化尤其重要，因为自动化的前提是覆盖要能自己跟着演进。

## 验证

这次实际运行了这些检查：

- `cargo fmt`
- `cargo test`
- `cargo run --release --bin indicator-bench`
- `./smoke`

结果上：

- Rust 测试通过
- 新增指标的 golden 对齐通过
- `atr` 的流式与批处理对齐通过
- release benchmark 成功输出新增指标的性能数据
- 旧 C 路径仍然通过

## 未覆盖项

这次还没有处理：

- `bbands`、`rsi`、`macd` 还没有流式 Rust 实现
- benchmark 仍然只覆盖 Rust registry，不对比 C 版本
- 还没有引入性能历史基线或阈值告警
- 还没有迁移 `dema`、`tema`、`trix`、`stoch` 这类更复杂或更连锁的指标

## 对新手的理解建议

可以把这次提交理解成“把 Rust 迁移从试验阶段推到可复制阶段”。

第一批更多是在证明：

- 能不能跑
- 能不能测
- 能不能 benchmark

第二批则是在证明：

- 这套结构是不是能覆盖更多类型的指标
- 新增指标时，测试和 benchmark 能不能自动跟上

如果以后继续看后续提交，你会发现很多新指标迁移都可以沿用这次建立下来的模式。
