# 默认用中文写提交教程

## 背景

这个仓库里的提交教程本来就是为了帮助人类跟上 AI 的开发速度。

既然主要读者是中文使用者，那么教程如果默认写成英文，就会凭空增加一道理解门槛：

- 新手先要翻译
- 再要理解背景
- 最后才能跟上代码变化

这会削弱 `tutorials/commit/` 目录本来最重要的价值，也就是“让人快速看懂每次提交为什么值得存在”。

## 主要目标

把规则写死在 [`/Users/dev/workspace2/hc_apps/tulipindicators/AGENTS.md`](/Users/dev/workspace2/hc_apps/tulipindicators/AGENTS.md) 里：

- 提交教程默认写中文
- 默认面向中文新手
- 英文只保留在命令、代码符号、函数名、API 名、行业缩写这些确实不适合翻译的地方

这样以后教程语言就不是“看作者心情”，而是仓库协作规范的一部分。

- 代码符号保留原文
- 命令保留原文

这比“强行全翻译”更适合工程文档。

这样以后 AI 在提交前就会主动检查这一点，而不是等人回头提醒。

## 关键知识

### 为什么教程和 commit message 不一样

commit message 是高密度摘要，强调：

- 为什么改
- 改了什么
- 怎么验证
- 没处理什么

而教程更像“带新人上手的解释文档”，强调：

- 这次背景是什么
- 为什么这样设计
- 相关知识点是什么
- 新手阅读时最容易卡在哪里

所以教程比 commit message 更需要照顾读者语言习惯。

### 为什么不是“中英双语全写”

看起来“双语全写”很全面，但实际常常会让文档更冗长、更累。

更实用的做法是：

- 说明用中文
- 术语保留英文
- 第一次出现时给中文解释

这样既不丢工程准确性，也不会让教程变成翻译练习。

## Rust / 协作知识点 1

工程文档里的“默认值”很重要。

如果规则只写“可以写中文”，那现实里就会变成：

- 有人写中文
- 有人写英文
- 有人中英混杂

最后风格会越来越散。

所以真正有用的规则通常是：

- 默认值是什么
- 例外何时允许

这次就是把“默认中文，必要时保留英文术语”明确下来。

## Rust / 协作知识点 2

对新手友好的文档，不等于把所有术语都翻译掉。

真正重要的是：

- 用读者熟悉的语言解释上下文
- 保留那些在代码里本来就要按原文搜索的词

例如：

- `cargo test`
- `run_in_place`
- `benchmark`

这些词保留原文通常更好，因为读者之后在代码和命令行里看到的也是这些形式。
