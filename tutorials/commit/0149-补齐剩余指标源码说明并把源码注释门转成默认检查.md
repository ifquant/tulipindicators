# 0149 - 补齐剩余指标源码说明并把源码注释门转成默认检查

这笔提交做的是发布前最后一类文档收口：不再把“指标源码要有解释性注释”当作未来事项，而是让它进入默认测试。

## 背景

前面几笔已经把 README、crate-level rustdoc、核心 API、状态 API、高频指标、分组指标和用户指南补齐了。但 `documentation_style` 里还有一个 ignored gate：它会扫描 `rust/src/indicators` 下的指标实现文件，要求每个源码文件至少有解释性注释。

这个 gate 失败的位置集中在一批独立指标文件上，例如 `ao`、`psar`、`bbands`、`kama`、`t3` 等。这些文件的运行时代码已经稳定，但源码入口缺少“这个指标在干什么、为什么状态这样组织”的快速说明。

## 变更

本次只做文档和测试门调整，不改变任何指标算法：

- 给剩余 41 个指标实现文件补文件级 `//!` 说明。
- 注释重点说明输入输出形状、滚动状态、warmup 或直接 kernel 的设计理由。
- 将 `indicator_source_files_have_explanatory_comments` 从 ignored 测试改成默认测试。

## 为什么用文件级注释

这里没有把每个局部变量都加注释，因为那会降低热循环代码的可读性。指标文件最需要的是入口解释：读者打开文件时先知道这个指标的计算意图、状态设计和输出约定，再按代码往下读。

文件级 `//!` 文档也能被 rustdoc 收集，比散落在实现内部的普通注释更适合发布阶段的源码导航。

## 经验点

文档 gate 最好从“存在性检查”开始。它不能证明注释一定完美，但能防止新增指标源码完全没有说明。等库稳定后，可以继续把 gate 提升到更强的规则，例如要求每个 public typed state 都有 rustdoc。
