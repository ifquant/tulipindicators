# 把 `crossover` 和 `floor` 这类超轻指标改得更贴近 C 的热循环

## 背景

这次处理的是两类很容易被忽视的热点：

- `crossover`
- `floor`

它们看起来都很简单，所以第一反应往往是“这里不可能慢多少”。  
但性能优化里经常恰恰相反：

- 指标本体越简单
- 通用 helper、函数指针、切片包装带来的固定成本就越显眼

所以这类指标的目标，不是“重写算法”，而是把热路径写得更像 C。

## 这次做了什么

### `crossover`

之前的 Rust 实现虽然已经是专门逻辑，但还是每轮都按 `index` 回看：

- `left[index]`
- `right[index]`
- `left[index - 1]`
- `right[index - 1]`

这次改成更贴近 C 的“前值推进”写法：

1. 先记住上一根的 `left/right`
2. 每次只取当前值
3. 算完后把当前值变成新的前值

这样热循环里少了一层“反复回看前一项”的味道。

### `floor`

`floor` 之前复用了通用 unary indicator helper。  
这套 helper 的优点是统一，但它会把：

- 通用函数
- `op` 函数指针
- 共用包装逻辑

一起带进热路径。

对于 `floor(sample)` 这种只有一个数学操作的指标，这些通用层就会显得偏重。  
所以这次给 `Floor` 单独写了：

- `run()`
- `run_in_place()`

让它直接走薄循环。

## 结果怎么理解

focused benchmark：

- `crossover 4096 = 1.195x`
- `crossover 65536 = 1.141x`
- `floor 4096 = 1.161x`
- `floor 65536 = 1.028x`

这次的价值在于：

- `crossover` 已经压进 `1.2x`
- `floor` 也明显改善

但它们还没有达到新的 `0.8x` 目标，所以只能算“继续收尾差”，不能算“已经极致”。

## 给 Rust 新手的两个知识点

### 1. 函数指针式 helper 很统一，但不一定适合超轻热路径

像这样：

```rust
run_unary(..., floor_op)
```

在代码组织上很舒服，但对极轻指标来说，统一接口本身就可能比真正的数学运算更贵。

这不是说 helper 不好，而是要学会分场景：

- 绝大多数地方：通用 helper 值得保留
- 极少数热路径：值得单独展开

### 2. “前值推进”是很多热循环里很常见的去噪写法

例如 `crossover`：

- 你当然可以每次都用 `index - 1` 回看前一项
- 但也可以先把“前一个值”放到局部变量里

后者通常更像底层 C 写法，也更容易把循环核心写清楚：

- 读当前
- 算输出
- 更新前值

这类写法在指标、状态机、parser、网络协议里都很常见。

## 这次没有包含什么

- 没有继续处理 `atr stream`
- 没有顺手优化 `lag`
- 没有把所有 unary simple 指标都改成专门实现，这次只收 `floor` 这一条确定有效的收益
