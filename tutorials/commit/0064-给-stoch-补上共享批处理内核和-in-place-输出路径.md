# 给 `stoch` 补上共享批处理内核和 `in-place` 输出路径

## 背景

这轮全量 benchmark 刷新以后，`stoch` 直接冲到了榜单最前面：

- `stoch 4096`
- `stoch 65536`

它和前面已经收掉的一些热点很像：

- 公式本身并不离谱
- C 版本已经是比较直接的 batch 实现
- Rust 版本虽然逻辑正确，但 batch 还没有 `run_in_place(...)`

这意味着 benchmark 在测它的时候，Rust 更容易吃到 owned `Vec` 分配和包装的成本。

## 这次主要做了什么

这次没有改随机指标的数学语义，只是把 batch 入口补完整：

- 抽出了共享的 `run_stoch_batch(...)`
- `run(...)` 直接预分配双输出缓冲区后调用共享内核
- 新增 `run_in_place(...)`
- `run_in_place(...)` 通过 `split_at_mut(...)` 把两路输出切片安全拆开，避免多重可变借用冲突

这样之后：

- 高层接口还是保留
- benchmark 和性能敏感路径可以走更薄的 `in-place` 路线

## 为什么这笔有效

focused benchmark 结果：

- `stoch 4096 = 1.123x`
- `stoch 65536 = 1.017x`

也就是说，它已经从原来接近 `3x` 的大热点，回到了接近 parity 的区间。

这说明这次主要差距确实不是算法本身，而是 batch 输出层还不够薄。

## 给 Rust 新手的两个知识点

### 1. 多输出指标做 `in-place` 时，常见的难点不是公式，而是借用规则

像 `stoch` 这种指标有两路输出：

- `stoch_k`
- `stoch_d`

如果你直接同时拿 `outputs[0]` 和 `outputs[1]` 的可变引用，Rust 很容易报多重可变借用错误。

这次用到的典型写法是：

```rust
let (first, second) = outputs.split_at_mut(1);
```

然后再分别取：

- `first[0]`
- `second[0]`

这样 Rust 能确定这两段内存不重叠，借用就合法了。

### 2. “共享 batch 内核 + 高层 API 包装” 是性能敏感 Rust 库里很常见的分层

这次的结构其实很典型：

- `run_stoch_batch(...)`
  - 真正的热路径内核
- `run(...)`
  - 负责分配和包装输出
- `run_in_place(...)`
  - 负责把调用方提供的切片接到同一个内核

这种分层的好处是：

- 不重复写公式
- 易用接口和高性能接口都能保留
- 后面 benchmark 也更容易直接测试内核真实成本

所以如果你以后写 Rust 的性能敏感库，看到这种三层结构，不要觉得它“多余”，它通常就是把易用性和性能拆开的办法。
