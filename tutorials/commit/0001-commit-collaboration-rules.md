# 0001 提交协作规则与教程目录的建立

## 背景

这个仓库已经开始明显进入“人和 AI 一起维护”的工作方式。
当改动越来越快、提交越来越密集时，单看 diff 和简短 commit message 往往不够，新手或者隔几天再回来看的人很容易跟不上：

- 这次改动为什么值得单独提交
- 这次改动解决的真实问题是什么
- 改动背后有什么上下文和领域知识
- 哪些问题还没有解决，不能误以为已经完成

所以，除了写好 commit message，还需要给每一次提交配一篇面向新手的教程。
这篇教程不是为了重复 diff，而是为了帮助人类跟上 AI 的工作速度和决策方式。

## 主要目标

这次提交要建立一套最小但可执行的协作机制：

- 在仓库中建立 `tutorials/commit/` 目录
- 规定以后每次提交都必须新增一篇教程
- 让教程文件按四位序号递增，方便按时间阅读和追踪
- 把“教程必须写什么”固化进 `AGENTS.md`

这样做的目的，是让提交历史不仅是“代码变了什么”，还包含“为什么这样变、怎么验证、接下来还差什么”。

## 改动概览

这次主要做了两类改动。

第一类，是修改 `AGENTS.md` 中的提交规则：

- 要求 `tulipindicators` 的每一次提交都必须新增一篇 `tutorials/commit/NNNN-*.md`
- 规定文件名必须以四位序号开头，范围 `0001` 到 `1000`
- 要求新教程必须使用下一个可用编号，不能复用旧编号，也不要跳号
- 明确教程要面向新手，解释背景、目标、关键知识、验证和未覆盖项

第二类，是建立目录和样板：

- 创建 `tutorials/commit/`
- 新增本篇 `0001-commit-collaboration-rules.md`

从现在开始，这个目录本身就会成为项目演化的一部分。

## 关键知识

### 1. 为什么 commit message 还不够

高质量 commit message 非常重要，但它仍然偏“摘要”。
它适合快速浏览、适合合并前审查，也适合以后 `git log` 检索。

但它通常不会展开解释：

- 这次改动前的历史背景
- 为什么方案 A 没选、而是选了方案 B
- 新手应该先理解哪些概念，才能读懂这次改动

教程文件正好补足这一层。

### 2. 为什么要编号

给教程文件加 `0001`、`0002` 这样的编号，有几个实际好处：

- 按文件名排序时，顺序就是提交叙事顺序
- 新人可以从头读，逐步理解项目演进
- AI 在生成教程时不需要发明命名体系，只要取下一个序号

四位编号也足够长，短期内不会因为排序问题变乱。

### 3. 为什么教程要写“未覆盖项”

AI 特别擅长快速推进局部实现，但这也容易带来一个风险：
局部可用的东西，在文字上看起来像“已经全部完成”。

所以教程和 commit message 都必须写清楚：

- 这次只覆盖了什么
- 还有什么没做
- 哪些路径还没验证

这对协作尤其重要，因为人类往往需要靠这些边界判断“下一步该做什么”。

## 这次规则想解决的协作问题

如果没有教程机制，未来会反复遇到这些问题：

- 提交历史能看出“改过”，但看不出“为什么这样改”
- 新手只能去猜背景，理解成本很高
- AI 分阶段提交时，边界不够清楚，容易误判进度
- 几周后回头看时，人类需要重新做上下文恢复

建立教程目录之后，每次提交都多了一层“面向人解释”的缓冲区。
这层缓冲区的价值，不在于重复代码，而在于保存决策上下文。

## 验证

这次改动以文档和规则为主，验证方式是人工检查：

- 确认 `AGENTS.md` 已加入“每次提交必须新增教程”的规则
- 确认 `tutorials/commit/` 目录存在
- 确认本篇教程文件名使用了四位编号 `0001`
- 确认教程内容面向新手解释了背景、目标和协作动机

## 未覆盖项

这次还没有处理以下内容：

- 还没有建立自动脚本去检查“提交前是否存在新的教程文件”
- 还没有建立教程索引页或目录总览
- 还没有规定当编号达到 `1000` 后的处理方式
- 还没有把这套规则推广到 `hc_apps` 里的其他子项目

## 对新手的阅读建议

以后阅读这个目录时，可以这样用：

1. 先看文件名，按编号理解项目演进顺序。
2. 再看 `背景` 和 `主要目标`，先理解“为什么改”。
3. 然后看 `改动概览` 和 `关键知识`，理解实现方向和相关概念。
4. 最后看 `验证` 和 `未覆盖项`，判断当前状态是否可继续依赖。

这样读，比直接从 diff 开始，会更容易跟上 AI 的思路。
