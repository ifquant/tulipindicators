## 这次结果怎么判断

这次最重要的不是“所有指标都追平了”，而是“剩下没追平的那部分更可信了”。

比较明显的点：

- `macd` 已经基本回到 parity
- `kama` 比之前明显更接近阈值
- 但 `apo / ppo / dema / tema / trix / zlema` 还没有完全追平

这说明现在这组剩下的慢，不再主要是因为缺少 `run_in_place` 这种公共接口层能力，而更像是：

- 多级 EMA 级联本身的状态更新成本
- 某些公式里仍有额外算术开销
- 或者 C 侧在这组上刚好非常薄

换句话说，这次是把“公共慢路径”先剥掉了。

## 新手 Rust 知识 1：为什么 `run_in_place` 不是“重复劳动”

很多新手第一次看到：

- `run()`
- `run_in_place()`
- `feed()`
- `feed_in_place()`

会觉得这像是在写重复代码。

但在性能敏感库里，这其实是在把两类需求分开：

- 高层易用接口：适合普通调用者
- 低层薄接口：适合 benchmark、热路径、预分配调用者

如果只保留高层接口，那你后面很难判断“慢的是算法”还是“慢的是分配和复制”。所以这类重复，很多时候是在换可控的性能边界。

## 新手 Rust 知识 2：为什么 `powi(2)` 不一定适合热循环

写 `powi(2)` 很直观，也很正确。但在性能敏感循环里，如果你只是在算平方，那么：

- `x * x`

通常更直接，也更容易让编译器和读代码的人一眼看懂“这里就是平方”。

这不是说 `powi` 不能用，而是：

- 当指数是编译期已知的小常数
- 而且循环本身又很热

直接乘法通常是更好的默认选择。

## 这次最值得记住的点

性能优化经常不是“一步到位”，而是分两层：

1. 先切掉公共接口税
2. 再看剩下的真热点

如果你一开始就把这两层混在一起，很容易一边怀疑算法，一边其实还在被框架开销误导。
