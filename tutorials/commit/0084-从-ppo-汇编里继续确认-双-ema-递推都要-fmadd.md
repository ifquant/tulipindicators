# 从 PPO 汇编里继续确认：双 EMA 递推都要 `fmadd`

这次改动只保留了 `ppo`，没有把同轮尝试的 `natr` 一起提交。原因很简单：`ppo` 的收益稳定，`natr` 没站住。这个仓库一直强调“每一笔提交都要能解释为什么值得留下”，所以这次教程也只讲已经证明有效的那一部分。

## 这次想解决什么问题

前一轮 focused benchmark 里，`ppo` 仍然比 C 慢：

- `ppo 4096 = 1.265x`
- `ppo 65536 = 1.361x`

它的结构和前面已经修好的 `apo` 很像，都是两条 EMA 递推链，只是最后一步输出公式不同：

- `apo` 输出差值
- `ppo` 输出百分比差值

所以这次的目标不是重写算法，而是确认：

1. C 的热循环是不是已经用了 `fmadd`
2. Rust 对应位置是不是还停留在 `fmul + fadd`
3. 如果是，就把 Rust 写法改成更容易生成 `fmadd` 的形式

## C 和 Rust 的关键差别

`ppo` 的核心递推本质上是：

```rust
short_ema = (sample - short_ema) * short_per + short_ema;
long_ema = (sample - long_ema) * long_per + long_ema;
```

这种写法在数学上没问题，但在机器码层面，编译器不一定会自动把它降成最理想的 fused multiply-add。

而 C 这边在对应热循环上，之前已经多次验证过：编译器会生成更贴近下面这种形状的指令链：

- `fsub`
- `fmadd`
- `str`

这说明如果 Rust 想更接近 C 的 zero-cost 热循环，不能只说“表达式数学上等价”，还得关心“编译器最终会认成哪种指令形状”。

## 这次实际怎么改

这次只改了 `ppo` 的两条 EMA 递推链：

```rust
short_ema = (sample - short_ema).mul_add(short_per, short_ema);
long_ema = (sample - long_ema).mul_add(long_per, long_ema);
```

注意这里有两个要点：

1. 不是只改一条链
2. 也没有去碰最后的百分比输出公式

因为真正的热点不是最后那次除法，而是每个样本都会执行的两次 EMA 更新。

## 为什么这笔值得单独提交

focused benchmark 的结果是：

- `ppo 4096 = 0.981x`
- `ppo 65536 = 0.958x`

也就是说，它已经从“稳定慢于 C”回到了 parity 区间，而且长输入下已经反超。

同轮我也试了 `natr`，但结果并不稳定：

- `65536` 看起来不错
- `4096` 却明显变差

所以 `natr` 全部回退，没有混进这次提交。

这也是一个很重要的人机协作原则：不要把“有一点希望”当成“已经值得保留”。

## 这次可以学到的 Rust 知识

### 1. `mul_add` 不只是语法糖

Rust 的 `f64::mul_add(a, b)` 不是单纯为了代码好看。它表达的是一个更强的意图：

```rust
x.mul_add(a, b)
```

表示希望编译器把它当成“乘加融合”的候选，也就是尽量生成一条 fused multiply-add 指令。

在数值内核里，这通常同时影响：

- 性能
- 舍入行为
- 指令条数

所以在性能敏感的递推公式里，`mul_add` 是值得主动考虑的工具。

### 2. “只改热循环”是一种很重要的优化纪律

这次没有去重构接口、没有改 benchmark、没有改 stream 结构，只改了热循环里最核心的两行。

这样做的好处是：

- 变量更少
- 收益更容易归因
- 一旦没有收益，也更容易回退

对新手来说，这个习惯非常重要：优化时不要一上来同时改五件事。先把真正的热点和最小改动绑定起来。

## 这次留下的结论

- `ppo` 和 `apo` 一样，真正值得优化的是两条 EMA 递推链
- 对这种双 EMA 指标，`mul_add` 要两边都补上
- 同轮实验里，如果别的指标没有稳定收益，就应该明确排除，不要顺手一起提交
