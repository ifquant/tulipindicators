# 0005 复杂指标的流式状态机实现

## 背景

前几次 Rust 迁移已经把一批常见和复杂指标接进了批处理路径：

- `bbands`
- `rsi`
- `macd`
- `dema`
- `tema`
- `trix`
- `stoch`

但“已经有批处理实现”并不代表迁移工作真的完成了。
对技术指标库来说，流式计算同样重要，因为调用方经常不是一次性拿到完整历史数据，而是会不断喂入新 bar。

这就带来一个更难的问题：

- 批处理可以回头看整段数组
- 流式实现只能依赖自己保存下来的状态

如果状态设计不对，就很容易出现这些问题：

- warm-up 区间和批处理不一致
- chunk 边界前后输出对不上
- 多阶段平滑指标在增量运行时漂移
- 窗口型指标为了偷懒每步全量重扫，性能明显退化

所以这次提交的重点不是“再加一个接口”，而是把现有复杂指标真正补齐到可流式运行的程度。

## 主要目标

这次提交主要解决三件事：

1. 为 `bbands`、`rsi`、`macd`、`dema`、`tema`、`trix`、`stoch` 增加 Rust stream 实现
2. 提取共享的 EMA 流式状态，避免多层 EMA 指标各自重复维护近似逻辑
3. 让现有 stream 对比测试和 benchmark 自动覆盖这些新增流式路径

做完之后，当前已迁移到 Rust 的主要复杂指标就不再只支持 batch，还能参与增量计算和持续性能观测。

## 改动概览

这次改动可以分成三层来看。

第一层是共享基础状态：

- 新增 `shared.rs`
- 抽出 `EmaState`

这样 `macd`、`dema`、`tema`、`trix` 这些依赖一层到三层 EMA 级联的指标，就可以复用同一套流式 EMA 推进逻辑，而不是每个文件都手工复制一遍“第一次输入如何初始化、后续如何平滑”的细节。

第二层是各指标自己的流式状态机：

- `bbands` 维护固定窗口、滚动和平方和，用于流式标准差计算
- `rsi` 维护上升量/下降量平滑状态
- `macd` 维护短 EMA、长 EMA 和 signal EMA
- `dema` / `tema` / `trix` 在共享 EMA 状态上做多层级联
- `stoch` 维护窗口最高/最低值和平滑中的 `%K` / `%D`

第三层是测试与验收：

- 现有 stream-vs-batch golden 对比会自动覆盖这些新路径
- benchmark 会自动输出这些指标的 stream 性能
- 对非常小的浮点差异放宽了 stream 对齐容差，避免把可接受的舍入噪声误报成行为错误

## 关键知识

### 1. 为什么复杂指标的 stream 实现更难

像 `sma`、`ema` 这种简单指标，状态机相对直接：

- `sma` 关心窗口和滚动和
- `ema` 关心上一个平滑值

但这次这批指标里，很多都不是“一层状态”。

例如：

- `macd` 需要三条相关联的 EMA
- `tema` 需要三层 EMA 串联后再组合
- `trix` 需要三层 EMA 后再算变化率
- `stoch` 需要窗口极值和两级平滑

这意味着不是把 batch 代码切成一行一行执行就能得到 stream 版本，必须先把“跨输入保留什么状态”想清楚。

### 2. 为什么要抽共享 `EmaState`

如果不抽共享状态，`macd`、`dema`、`tema`、`trix` 很容易都各自维护：

- multiplier
- 上一次 EMA 值
- 初始化时的第一笔输入处理

这样会有两个问题：

- 同一个规则在多个文件里重复实现，后续修边界时容易不一致
- 多层 EMA 指标的代码会被样板逻辑淹没，可读性下降

把 `EmaState` 抽出来后，可以把注意力放回“这个指标由几层 EMA 组成、输出怎么组合”，而不是反复处理同一种平滑细节。

### 3. 为什么 `stoch` 不能用最朴素的窗口重扫

`stoch` 每步都要知道当前窗口内的最高值和最低值。

最朴素的办法是：

- 每来一个新点
- 把整个窗口重新扫一遍找最大最小

这种写法虽然容易写，但在 stream 模式下会把每一步都变成额外的窗口扫描，性能会比批处理差很多。

这次实现里用了单调队列来维护窗口极值，这样：

- 新数据进来时可以把不可能再成为极值的旧元素弹掉
- 老数据滑出窗口时也能及时丢弃
- 大多数时候不需要全窗口重扫

这更接近高性能流式指标应该有的实现方式。

### 4. 为什么 stream 对齐测试这么重要

对调用方来说，理想情况是：

- 一次性跑完整历史数据
- 分块喂入同样的数据

这两种方式应该得到相同结果。

如果 stream 路径和 batch 路径不一致，使用者通常很难立刻定位问题，因为出错点可能不是当前 bar，而是更早某一步状态没有正确保留下来。

所以这次保留了 batch-vs-stream 自动对比测试，把“分块执行是否仍然对齐”作为基本验收条件。

## 验证

这次实际运行了：

- `cargo fmt`
- `cargo test`
- `cargo run --release --bin indicator-bench`
- `./smoke`

结果上：

- Rust 测试通过
- 新增 stream 指标都能参与 batch-vs-stream 对比
- benchmark 能输出这些指标的 stream 性能数据
- 旧 C 路径仍然通过

## 未覆盖项

这次还没有处理：

- 还没有把 Rust benchmark 扩展成 C 与 Rust 的直接对比基准
- 还没有为未迁移的复杂指标继续补 stream，例如后续可能出现的派生指标
- 当前 stream 对齐容差做了小幅放宽，用于容纳极小浮点噪声，但还没有针对每个指标做更细的误差分层策略

## 对新手的理解建议

可以把这次提交理解成“把复杂指标从能离线算，推进到能增量算”。

前几次迁移更多是在证明：

- Rust 版本能不能复现结果
- 测试和 benchmark 基础设施能不能跟上

而这次开始证明：

- 状态型复杂指标能不能稳定跨 chunk 保持一致
- 多层 EMA 和窗口极值逻辑能不能在流式模式下继续保持正确与高效

如果你后面继续看这个仓库的 Rust 演进，这次会是一个很关键的节点，因为它标志着“批处理迁移”开始进入“实时增量计算迁移”阶段。
