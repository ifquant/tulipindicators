# 对齐 Rust beta 测试到 C batch 真值

## 这次改动想解决什么

前面 Rust 已经把稳定指标和 beta 指标都迁完了，但“迁完”不等于“测试已经真正和 C 对齐”。  
现有 Rust 测试主要靠 golden data；这能覆盖很多场景，但它并不能直接回答一个更关键的问题：

- Rust 当前输出，是否真的和现有 C 实现一致？
- 如果不一致，是 Rust 算错了，还是 C 自己的 ref / stream 路径本来就和 batch 不一致？

这次提交的目标，就是把这个问题拆开：

- 先把 `C batch` 明确当成当前仓库的真值来源
- 再让 Rust beta 指标逐个去和这个真值对齐
- 避免被 C beta 内部那些历史上就不完全一致的 ref / stream 路径误伤

## 这次做了什么

### 1. 新增一个最小 C oracle

新增了一个测试辅助程序，它会：

- 编译 beta 指标的 C 实现
- 接收 Rust 生成的输入数据
- 调用对应的 C batch 指标函数
- 把输出序列吐回给 Rust 测试

这样 Rust 侧就能直接做“同一组输入，对比 C 输出和 Rust 输出”。

这里有一个重要设计选择：

- 我们没有把 C 的 `ref` 或 `stream` 结果再拿来作为 beta parity 的强制门槛
- 因为有些 beta 指标在 C 仓库里，`stream` 本来就不一定和 `batch` 完全一致

如果这里强行要求 “C batch == C stream == Rust stream”，测试会被历史包袱卡死，反而看不清真正的迁移正确性。

所以这次先收窄目标：

- `Rust batch` 必须对齐 `C batch`

这是更稳、更能推进迁移的第一性目标。

### 2. 新增 Rust beta parity 测试

新增的 Rust 集成测试会：

- 为每个 beta 指标构造一套确定性的 synthetic 输入
- 运行 Rust 指标
- 调用 C oracle
- 对每个输出值逐点比较

这样一来，beta 指标不再只是“看起来能跑”，而是有一条真正的跨语言对账链。

### 3. 顺手修了一个真实差异：`kst`

跑 parity test 时，第一个爆出来的是 `kst`。

问题不在参数顺序，而在状态预热。

C 版本会在到达 `roc4` 之前，就分别预热四条 ROC 的 EMA。  
Rust 之前的写法则是“等四条都 ready 了，再一起开始 feed”，这会让最早一段结果整体偏掉。

这次把 Rust 的 `kst` 改成了更贴近 C 的方式：

- 每条 ROC-EMA 只要自己有足够历史，就提前开始预热
- 真正输出 `kst` 时，再把四条已经预热好的 EMA 合成

这个修正说明了 parity test 的价值：

- 它不只是“多一层测试”
- 它能把看不出来的初始化差异直接抓出来

## 为什么这对人机协作重要

如果没有这种跨语言对账测试，AI 迁移指标时很容易出现一种危险情况：

- 结构看起来对
- 单元测试也大致通过
- 但某些初始化阶段、边界窗口、平滑器预热路径和原版并不一致

对新手来说，这类错最难发现，因为代码表面上“非常像”，而且数值只在前几项偏一点。

有了 C oracle 之后，协作方式就更清楚了：

- 人负责决定“现阶段以什么为真值”
- AI 负责快速批量迁移并不断对账
- 一旦对不上，先收窄到某个具体指标和具体位置，再修

这比泛泛地说“看起来实现差不多”要可靠得多。

## 新手知识点 1：`OnceLock` 适合做“测试时只构建一次”的懒初始化

这次 Rust 测试里用了 `OnceLock<PathBuf>` 来缓存 beta oracle 的路径。

它适合这种场景：

- 第一次跑测试时，需要做一笔昂贵操作
  - 例如编译一个 C helper
- 之后同一个测试进程里，所有 case 都复用这份结果

直观理解可以把它看成：

- “只允许初始化一次的全局盒子”

这样你就不用每个 case 都重新编译一遍 C helper，也不用自己写一堆脆弱的全局状态锁。

## 新手知识点 2：流式指标最容易错的地方不是公式，而是“预热时机”

像 `kst` 这种带多条内部 EMA 的指标，最容易错的通常不是最终加权公式，而是：

- 每条内部状态什么时候开始喂数据
- 第一批可输出值到底应该落在哪一根 bar

这是流式实现和批处理实现最常见的偏差来源。

一个很有用的设计习惯是：

- 不要只想“公式怎么写”
- 还要明确写下“每个内部状态从第几根 bar 开始有效”

如果你以后读类似代码，优先看这三件事：

1. 历史窗口从哪里取值
2. 内部平均器从什么时候开始初始化
3. 第一个输出是在什么条件下产生

大多数对不齐，最后都能归到这三类问题上。

## 这次改动后的结论

现在 beta 指标这条线已经有了：

- Rust golden tests
- Rust stream vs batch tests
- Rust beta vs C batch parity tests

这三层放在一起，比单独靠任何一层都更靠谱。后面如果继续优化实现或改 stream，至少不会失去和原 C 版本的数值锚点。
