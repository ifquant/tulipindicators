# 给 `rsi` 补上 `in-place` 批处理路径，并解释为什么长输入还会留尾差

## 背景

这次重新看 `rsi`，一眼就能发现一个很具体的问题：

- 它已经有正确的 batch 实现
- 但还没有 `run_in_place()`

这意味着 benchmark 在测 Rust 的时候，只能走：

- 分配 `Vec`
- `push`
- 再把拥有所有权的结果返回

对于性能敏感库来说，这会把 API 层成本直接带进热路径。

## 这次做了什么

这次没有改公式，也没有改数学语义，只做了结构上的补齐：

- 抽出共享 `run_rsi_batch(...)`
- `run()` 改成预分配输出后调用这条 batch kernel
- 新增 `run_in_place()`
- 顺手把 `stream` 也补上了 `feed_in_place()`

重点不是“代码更优雅”，而是：

- 让 `rsi` 和其他已经做过性能分层的指标一致
- 让 benchmark 能走调用方提供输出缓冲区的路径

## 结果怎么理解

focused benchmark：

- `rsi 4096 = 1.109x`
- `rsi 65536 = 1.419x`

这组数字说明两件事：

1. 这笔改动确实有效
2. 但它不是全部问题

也就是说：

- 原来确实有一部分慢，是因为没有 `in-place` 批处理路径
- 剩下的差距，则更像是内核写法或共享平滑状态的尾差

## 给 Rust 新手的两个知识点

### 1. “没有 `run_in_place()`” 本身就可能是性能 bug

很多人会把性能问题理解成：

- 算法写错了
- 循环太慢了

但在 Rust 这种强调所有权的语言里，接口形状本身就会决定很多成本。

如果一个指标只有：

```rust
fn run(...) -> Result<Vec<Vec<Real>>, IndicatorError>
```

那它天然就会带着：

- 分配
- 扩容或预分配
- 返回 owned 数据

这不一定错，但对 benchmark 来说，往往已经比 C 的“调用方给 buffer”更重了。

### 2. 先把“接口层税”切掉，再谈内核细抠

性能优化里很常见的误区是：

- 一上来就研究最细的循环

但如果接口层本身还在白白花钱，那你先抠循环，收益往往不大。

这次 `rsi` 的过程就是一个很典型的顺序：

1. 先补齐 `run_in_place()`
2. 再看剩下的尾差还有多少
3. 如果还慢，再去看内核本体

这个顺序通常比“先想办法写更花的数学循环”更稳。

## 这次没有包含什么

- 没有继续优化 `wilders`
- 没有去动 `ema` 和 `macd`
- `rsi` 还没有达到 `0.8x` 的新目标，这次只是切掉了明显的接口层成本
