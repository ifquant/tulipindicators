# 加一个轻量 style check，拦住测试和示例里新长出来的 `run(...)` 再取 `batch[0]` 写法

前面已经做了两件事：

1. 给单输出指标补了 `run_single(...)`
2. 把现有一批测试和文档调用点迁到了新接口

但如果没有约束，后面很容易又长回去。尤其是测试和示例，写的人通常图快，会自然写成：

```rust
let batch = Rsi.run(&[&input], &[14.0])?;
let expected = &batch[0];
```

所以这次补的是一个低成本的防回退检查。

## 为什么不用复杂静态分析

这类风格问题不值得引入重量级 lint 基础设施，也不适合做 AST 级分析。我们要的只是：

- 在最容易长回去的地方提醒人
- 成本足够低，默认就能跑
- 允许少量合理例外

integration test 刚好满足这三个条件。

## 这次怎么做

新增 `rust/tests/run_single_style.rs`，并注册到 `Cargo.toml`。

它做两件事：

1. 扫 `README.md`、`tutorials/state-api.md`、`rust/src/lib.rs` 的 Rust 代码块
   - 如果代码块里出现 `batch[0]`，直接失败
   - 这样可以防止新示例继续教人手拆第一输出

2. 扫测试文件里的 `batch[0]`
   - 默认视为不允许
   - 只对白名单放行

白名单只保留两类合理例外：

- 多输出指标测试，例如 `dm`、`di`、`macd`、`stoch`
- `single_output_api` 里故意拿老路径第一输出和 `run_single(...)` 做对照

## 这个检查的边界

它不是“证明某段代码一定是单输出 misuse”的完备分析器，而是一个面向仓库习惯的回归防线。

优点是：

- 简单
- 默认就跟着 `cargo test` 一起跑
- 失败信息直接告诉你该改成 `run_single(...)`

代价是：

- 合法例外需要显式白名单
- 如果以后测试结构大改，白名单要一起维护

这个取舍是合理的，因为我们要的是“尽量别让坏模式再长出来”，不是“做一个完美的 Rust 语义分析器”。
