# 把 wilders 的批处理和流式状态摊平成更直接的局部状态机

这次改动的背景，是 `wilders` 在 focused benchmark 里一直是个真热点。前面看源码时，它表面上已经不算很复杂了，但二进制和基准都说明：

- 它仍然明显慢于 C
- 而且慢的不只是 stream，batch 也慢

所以这次的目标，不是继续做更大的抽象，而是反过来把它摊平：

- batch 用更直接的指针式热循环
- stream 不再每个 sample 都绕 `WildersAverageState::feed()` 的 `Option` 分发

## 这次做了什么

这次主要改了两部分。

第一部分是 batch：

- `run_wilders_batch(...)` 改成了更接近 C 的指针前进方式
- 初始窗口求和和后续更新都直接在一个更薄的内存前进路径里完成

第二部分是 stream：

- `WildersStream` 不再把状态完全包在 `WildersAverageState` 里
- 改成自己直接维护：
  - `period`
  - `warmup_sum`
  - `value`
  - `progress`
- 再通过 `feed_sample(...)` 做最小状态推进

也就是说，这次做的是“把共享状态抽象拆开”，让这个指标自己管理更贴近公式的状态。

## 为什么这样做

共享状态抽象通常有好处：

- 复用逻辑
- 少写重复代码
- 更容易保证行为一致

但在性能敏感路径里，也会有代价：

- 每个 sample 都要走一次额外函数层
- `Option<Real>` 这种返回值在热循环里会不断参与分支
- 编译器不一定总能把这层抽象完全压平

`wilders` 这次就很像这种情况：

- 抽象本身没错
- 但它确实在拖热循环

所以这里更合适的做法，是让 `wilders` 自己维护最贴近公式的状态。

## 这次的效果

focused benchmark 的结果从之前的：

- `wilders batch 4096 = 2.671x`
- `wilders batch 65536 = 1.580x`

变成了：

- `wilders batch 4096 = 1.686x`
- `wilders batch 65536 = 1.764x`

这里要诚实地说清楚：

- `4096` 明显改善了
- `65536` 没有追平 C，而且不同轮次会有一定波动

但从 Rust 自己的 best 看，这次已经把 `wilders` 的内部实现推进到一个新的最好档位了，所以这笔依然是有效收敛。

## 新手知识点 1：抽象“正确”不等于抽象“免费”

Rust 新手很容易把“抽象写得很漂亮”和“运行时也一定很好”混在一起。

其实不是。

像 `WildersAverageState` 这种抽象：

- 语义上合理
- 结构上清楚
- 复用上也很好

但如果它正好处在每个 sample 都要经过的热循环里，就可能变成真实成本。

所以性能调优时，要敢于问一句：

> 这个抽象是不是正好放在了最不该放的地方？

## 新手知识点 2：局部状态机通常比频繁返回 `Option` 更容易压薄

如果你的热循环是：

- 每次输入一个 sample
- 维护几项简单状态
- 偶尔才产出结果

那么一种常见优化方向就是：

- 不让外部 helper 每次都返回 `Option`
- 而是在本地状态机里自己决定什么时候开始输出

这样做的好处是：

- 状态推进更集中
- 分支更可控
- 编译器更容易把循环看成一整段

## 这次最重要的经验

当一个指标已经确认是热点，而共享状态抽象正好位于每次 sample 的必经路径上时，把它摊平成局部状态机，往往是值得试的一刀。

它不一定一次就追平 C，但很容易先把最显眼的那层抽象税收掉。
