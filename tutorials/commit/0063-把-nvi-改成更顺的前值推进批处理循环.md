# 把 `nvi` 改成更顺的前值推进批处理循环

## 背景

这一轮原本是想继续从 `dema / cvi` 往下打，但 focused benchmark 重新筛下来之后，`nvi` 反而成了一个更值得先收的点：

- 公式很轻
- C 和 Rust 的数学逻辑本来就几乎一样
- 但 benchmark 里 Rust 仍然能慢到 `2x+`

这种情况通常说明：

- 不是算法选错了
- 也不一定是大架构问题
- 更可能是热循环的写法还不够顺

## 这次主要做了什么

这次没有改 `nvi` 的公式定义，只是把 batch 路径重写成了一个更明确的共享内核 `run_nvi_batch(...)`：

- `run(...)` 现在直接预分配输出并调用共享内核
- `run_in_place(...)` 也复用同一条批处理逻辑
- 循环里显式维护：
  - `prev_close`
  - `prev_volume`
  - 当前累计的 `nvi`

这比原来每步都通过索引反复去取“前一个值”和“当前值”更像 C 那种“顺着数据往前走”的写法。

## 为什么这次值得单独提交

因为结果很干净：

- `nvi 4096 = 0.984x`
- `nvi 65536 = 0.957x`

也就是说，这笔已经把 `nvi` 从明显热点收回到了接近 parity 的区间。

它的意义不只是收一个指标，而是再次证明了一个规律：

- 对公式很轻的指标，Rust 侧的性能差距往往不是“数学慢”
- 而是“热循环写法还没有足够贴近数据访问模式”

## 给 Rust 新手的两个知识点

### 1. `split_first()` 很适合处理“第一个元素特殊，后面统一处理”的循环

像 `nvi` 这种指标，第一个输出总是固定初值，后面的每一步才依赖“前一个 close / volume”。

Rust 里可以这样写：

```rust
let Some((&first, rest)) = slice.split_first() else {
    return 0;
};
```

它的好处是：

- 空输入可以自然提前返回
- 第一个元素的特殊逻辑和后续循环分开
- 后面的代码读起来更清楚

这在很多技术指标里都很好用，因为很多指标都有“warmup 第一个点”和“后续 steady-state”这两段。

### 2. “顺着数据往前推进”的循环，往往比“反复按索引回看前值”更容易优化

这次 `nvi` 的核心不是用了什么高级技巧，而是把逻辑改成：

- 记住 `prev_close`
- 记住 `prev_volume`
- 每处理一个新样本，就更新这两个前值

这种写法的好处是：

- 代码更贴近指标定义
- 不需要每一步都写 `slice[index - 1]`
- 在性能敏感路径里，也更容易得到稳定收益

所以对 Rust 新手来说，一个很实用的经验是：

- 如果你的循环本质上是“状态推进”
- 那就优先把它写成“显式维护状态”的形式
- 不要默认所有东西都靠索引回看

## 这次没有包含什么

- `dema` 的分段循环实验已经回退，因为它改坏了输出长度
- `cvi` 这条线仍然没有形成稳定收益，所以没有混进本次提交
- 这次只收 `nvi`，没有顺手动 `pvi` 或其他同类指标
