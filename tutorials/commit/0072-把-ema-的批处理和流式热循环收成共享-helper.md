# 把 ema 的批处理和流式热循环收成共享 helper

这次改动的背景，是前面做二进制对照时发现 `ema` 的热循环本体其实不算离谱，但 Rust 版本还是明显慢于 C。于是这次不去动公共契约检查，而是先收敛另一个更明确的问题：

- `batch`
- `stream`

这两条路径各自保留了一份自己的热循环写法，容易让机器码不够一致，也更难持续压薄。

所以这次的主要目标，是先把 `ema` 的核心更新逻辑收成共享 helper，让 batch 和 stream 都尽量走更薄、更统一的机器码。

## 这次做了什么

我把 `ema` 的 batch 路径抽成了：

- `run_ema_batch(input, multiplier, output)`

然后让：

- `run()`
- `run_in_place()`

都复用这条 helper。

同时，`EmaStream` 的实现也做了对应收敛：

- `feed()` 不再自己单独维护 `Vec::push` 循环
- 改成直接复用 `feed_in_place()`
- `feed_in_place()` 也改成了更直接的指针前进形式

这样做的核心目的不是“代码更短”，而是：

- 让 batch/stream 的热路径更接近
- 让编译器更容易产出一致、可控的机器码

## 这次的效果

focused benchmark 的结果是：

- `ema batch 4096`: `1.775x -> 1.326x`
- `ema batch 65536`: `1.330x -> 1.230x`

这说明：

- 改动是有效的
- 但还没有完全追平 C

所以这笔提交的定位应该是：

- 一次有效收敛
- 不是最终收尾

## 为什么这次没直接追平

这次还没追平，很重要的原因是我这刀没有动公共契约检查。

Rust 版 `ema` 在进入热循环前，仍然会走这些公共层：

- `single_input(...)`
- `parse_period(...)`
- `validate_output_slices(...)`
- `ensure_output_len(...)`

这些东西在安全公共 API 里是合理的，但对 `ema` 这种很薄的指标来说，占比会很显眼。

也就是说，这次主要收掉的是：

- 热循环重复实现
- 一部分机器码厚度

还没动的是：

- 安全公共接口的前置税

## 新手知识点 1：共享 helper 不只是为了“少写重复代码”

很多新手会把“抽 helper”理解成单纯的代码整洁问题。

在性能敏感代码里，共享 helper 还有一个额外价值：

- 它会让不同调用路径更容易复用同一套机器码模式

如果 `run()`、`run_in_place()`、`feed()`、`feed_in_place()` 各写一份相似但不完全一样的循环，编译器可能给你生成四种不同形态的机器码。  
一旦其中一份变厚，你调优就会更难追。

## 新手知识点 2：`unsafe` 指针前进的价值，在于把边界保证移到外层

这次 helper 里用到的 `unsafe`，重点不是“Rust 只要 unsafe 就会更快”，而是：

- 外层已经做过输入长度、输出长度检查
- 进入热循环后，剩下的是规则、线性的内存前进

这时用指针前进，可以减少每步都重新做边界检查的机会。

这是一种常见的性能敏感 Rust 分层方式：

- 边界层保证安全
- 热循环只做真正有价值的工作

## 这次最重要的经验

当一个指标的公式本身很简单，但实现里有多条相似热路径时，先把它们收成共享 helper，通常是值得的。

这样做不一定一次就追平 C，但很容易先把明显的重复成本和机器码分叉问题收掉。
