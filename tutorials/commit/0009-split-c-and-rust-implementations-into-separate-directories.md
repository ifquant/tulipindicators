# 拆分 C 与 Rust 实现目录

## 这次改动的背景

这个仓库最开始是一个典型的 C 项目。后面为了按 `plan.md` 逐步把核心指标改写成 Rust 风格，我们又在仓库根目录直接加入了 `Cargo.toml`、`src/` 和 Rust 测试。

这样虽然能工作，但对人和 AI 协作都不够清晰：

- 新人很难一眼看出哪些文件属于稳定的 C 实现，哪些文件属于正在迁移的 Rust 实现
- 修改构建、测试、生成脚本时，容易把两套实现的文件混在一起理解
- 后面继续迁移指标时，也不利于统计“C 还剩多少，Rust 已覆盖多少”

所以这次改动的目标不是增加新指标，而是把仓库结构整理清楚。

## 主要目标

这次提交想解决三个问题：

1. 让 C 实现和 Rust 实现一眼分开。
2. 保留仓库根目录作为统一入口，不破坏已经形成的 `make` / `cargo` 使用方式。
3. 让现有验证链继续可用，包括 C smoke test、amalgamation 测试和 Rust golden test。

## 这次具体做了什么

### 1. 把 ANSI C 实现收拢到 `c/`

下面这些内容都移到 `c/` 下：

- 指标实现：`c/indicators/`
- beta 指标：`c/beta/`
- 工具与缓冲区代码：`c/utils/`
- golden 数据：`c/tests/`
- 代码生成模板：`c/templates/`
- 示例、基准、模糊测试、smoke 程序
- 生成产物和公共头文件：`c/indicators.h`、`c/candles.h`、`c/tiamalgamation.c`

这样做之后，`c/` 就明确表示“当前完整可用的 C 版本”。

### 2. 把 Rust 实现收拢到 `rust/`

Rust 相关内容统一移到：

- `rust/src/`
- `rust/tests/`

这样后续继续迁移指标时，Rust 侧的代码组织也更清楚，不会再和 C 根目录源码混放。

### 3. 保留根目录入口，避免使用方式突然变化

虽然实际代码移了目录，但没有要求使用者改变入口命令：

- 根目录 `Makefile` 现在只是一个轻量包装层，会把目标转发到 `c/`
- 根目录 `build.tcl`、`doc.tcl` 也只是包装层，会切到 `c/` 再执行真实脚本
- 根目录 `Cargo.toml` 仍然保留，但把库、测试和 benchmark 的路径改到 `rust/`

这一步很重要，因为它让“内部结构变清晰”和“外部使用习惯稳定”同时成立。

## 为什么这对人机协作有帮助

对 AI 来说，这种目录拆分会降低误判：

- 讨论 C 兼容性问题时，优先看 `c/`
- 讨论 Rust 迁移进度和风格时，优先看 `rust/`
- 跑 C 验证时，知道 golden 数据和生成链都在 `c/`

对人来说，这种结构也更容易维护心智模型：

- `c/` 是当前完整实现
- `rust/` 是迁移中的新实现
- 根目录是统一入口和仓库级文档

## 这次验证了什么

这次不是纯粹“搬文件”，因为目录调整很容易把脚本入口和测试路径弄坏，所以需要确认根目录命令仍然可用。

实际跑过：

- `make clean`
- `make smoke`
- `make smoke_amal`
- `cargo test`
- `cargo run --release --bin indicator-bench`

这说明：

- 根目录 `make` 仍然能驱动 `c/` 的构建和测试
- 单文件 amalgamation 生成链仍然可用
- 根目录 `cargo` 仍然能驱动 `rust/` 的库、测试和 benchmark
- Rust golden test 仍然能正确读取 `c/tests/` 中的已有数据

## 这次没有做什么

这次改动没有处理下面这些事情：

- 没有新增指标实现
- 没有修改指标数学语义
- 没有引入 C FFI 兼容层
- 没有为 `c/` 或 `rust/` 再分别增加更细的子目录 `AGENTS.md`
- 没有把所有文档都重写成新目录结构，只更新了这次重排直接相关的入口说明

## 新手读完后应该记住什么

如果你以后继续看这个仓库，可以先用这个判断法：

- 想看原始 Tulip Indicators 的完整实现，去 `c/`
- 想看 Rust 迁移结果和新架构，去 `rust/`
- 想跑原有 C 验证，从仓库根目录直接 `make smoke`
- 想跑 Rust 测试和 benchmark，从仓库根目录直接用 `cargo`

这就是这次提交最核心的价值：不是多了新功能，而是让仓库结构更适合持续迁移、持续验证、持续协作。
