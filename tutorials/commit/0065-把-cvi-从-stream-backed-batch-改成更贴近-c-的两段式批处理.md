# 把 `cvi` 从 `stream-backed batch` 改成更贴近 C 的两段式批处理

## 背景

`cvi` 这条线我前面其实已经碰过一次，但那次实验不够稳，所以没有提交。

这次重新回来做它，是因为新的 focused benchmark 仍然显示它是稳定热点之一，而且问题形态很明确：

- C 版本是直接的 batch 循环
- Rust 版本还在 `run() -> stream.feed()` 这条路径上

这种差异很典型，通常值得再试一次，但要比上一次更贴近 C 的结构。

## 这次主要做了什么

这次没有去改 `stream` 实现，只处理 batch 路径：

- 给 `cvi` 增加了 direct batch kernel：`run_cvi_batch(...)`
- `run(...)` 改为直接预分配输出再调用 batch kernel
- 新增 `run_in_place(...)`

新的 batch kernel 是按 C 版本的两段式结构写的：

1. 先做 warmup，把 EMA 和 lag ring 填满
2. 再进入 steady-state，一边更新 EMA，一边读出旧值计算输出

这样做的目的，不是“写得更聪明”，而是“写得更像 C 正在做的事”。

## 结果怎么理解

focused benchmark 结果：

- `cvi 4096 = 1.372x`
- `cvi 65536 = 1.418x`

这次的判断必须诚实：

- 有改善
- 但还没有追平
- 所以它是“有效收益的一步”，不是“已经解决”

这也是为什么这次值得单独成一笔提交：

- 因为它确实把路径从 `stream-backed batch` 切掉了
- 但也要明确写清楚：剩下的差距还在

## 给 Rust 新手的两个知识点

### 1. `batch` 和 `stream` 在语义上可以复用，但在性能上不一定该复用

很多时候你会觉得：

- 反正 `stream` 每次喂一个样本
- `batch` 不就是把一整段样本都喂进去吗

所以写成：

```rust
let mut stream = ...;
stream.feed(inputs)
```

看起来很自然。

但性能敏感库里，经常恰恰不该这么做。因为 `stream` 路径通常会带着：

- 状态对象
- 分支
- 可增长输出
- 额外的 warmup 逻辑包装

而 C 版的 batch 往往就是一条非常薄的循环。

所以一个很重要的经验是：

- 正确性上能复用，不代表性能上该复用

### 2. “两段式循环”是很多指标批处理优化里很常见的模式

这次 `cvi` 的批处理拆成了两段：

- 第一段：warmup
- 第二段：steady-state

这类写法在技术指标里特别常见，因为很多指标都有：

- 前期先累计/预热
- 后期再稳定地产生输出

把这两段显式写开，有两个好处：

- 代码更贴近数学/算法阶段
- 热路径里能减少不必要的条件判断

所以当你以后看到技术指标代码里有两层循环，不一定是“写复杂了”，很可能是在表达这两个阶段。

## 这次没有包含什么

- 没有继续优化 `atr stream`
- 没有顺手处理 `kvo`
- `cvi` 的 stream 路径本身也没改，这次只收 batch 路径的有效收益
